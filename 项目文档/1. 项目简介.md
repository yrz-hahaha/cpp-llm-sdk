# 1. 人工智能的发展：从符号主义到大语言模型

## 1.1 AI 的诞生：机器能否拥有智能？

人工智能最初面对的，并不是某一种具体算法，而是一个更基础的问题：**机器能否表现出类似人类的智能？**

Alan Turing 曾从计算的角度讨论“机器能否思考”，并提出后来被称为“图灵测试”的思想：与其争论机器是否真正拥有思想，不如观察它能否表现出足够接近人类的智能行为。1956 年的达特茅斯会议进一步推动了这一方向，“Artificial Intelligence”开始成为一个相对独立的研究领域。

从这一时期开始，“智能”逐渐从哲学讨论变成了一个工程问题：能否把知识、推理、学习等能力转化为计算机可以执行的过程？

## 1.2 符号主义与专家系统：让机器按照规则思考

早期人工智能的重要思路是**符号主义**：如果人类能够把知识整理成明确的事实和规则，计算机就可以按照逻辑进行推理。

专家系统是这一思想的典型应用。系统通常保存大量类似“**IF 某个条件成立，THEN 得出某个结论**”的规则，再根据输入逐步推导结果。MYCIN 等系统证明，在范围明确、规则相对稳定的专业领域中，计算机确实可以模拟一部分专家决策过程。

但问题也很明显：规则必须由人手工编写。现实问题越复杂，规则数量越庞大，规则之间还可能互相冲突。更重要的是，真实世界充满模糊性和例外情况，很难被有限的规则完全描述。

于是，一个新的问题出现了：**既然人类无法穷举所有规则，能不能让机器自己从数据中发现规律？**

## 1.3 机器学习：从人工编写规则到数据驱动

机器学习带来了 AI 思想上的一次重要转变。

过去是：

**人类总结规则 → 编写程序 → 计算机执行规则**

机器学习则变成：

**人类提供数据 → 算法从数据中学习规律 → 模型进行预测**

Logistic Regression、Decision Tree、SVM、神经网络等方法虽然原理不同，但共同推动了这种“数据驱动”的范式。神经网络中的反向传播等技术，也让模型能够根据训练结果不断调整内部参数。

不过，传统机器学习仍然很依赖人工设计**特征工程（Feature Engineering）**。例如进行图像识别时，人们往往需要事先告诉模型哪些边缘、纹理或形状值得关注。

这又带来了新的问题：**模型能不能不仅学习如何判断，还能自己学习什么特征最重要？**

## 1.4 深度学习：机器开始自己学习特征

深度学习的核心价值之一，就是让模型能够从原始数据中逐层学习特征，而不必完全依赖人工设计。

它真正取得突破，并不是单一技术突然出现，而是**算法、数据和算力**同时逐渐成熟。更大的数据集提供训练材料，GPU 提供大规模并行计算能力，更深的神经网络开始具备实际训练的可能。

2012 年，AlexNet 在 ImageNet 图像识别任务中的表现成为一个重要节点。它证明，在足够的数据和计算资源支持下，深度神经网络能够明显超过许多传统方法。随后，CNN 在计算机视觉中快速发展，而 RNN、LSTM 等网络被广泛用于语言和序列处理。

但 RNN 类模型通常需要按照顺序逐步处理文本，一个词处理完才能继续下一个词。这种方式不利于并行计算，同时在处理很长的上下文时也容易遇到困难。

如果模型能够不再严格按照顺序读取文本，而是直接分析文本中不同位置之间的关系，就可能突破这些限制。Transformer 正是在这样的背景下出现的。

## 1.5 Transformer：现代大模型的技术基础

2017 年，《Attention Is All You Need》提出了 Transformer 架构，并成为现代大语言模型最重要的技术基础之一。

可以简单理解为：过去的 RNN 更像是“从左到右逐词阅读”，而 Transformer 中的 **Self-Attention（自注意力）** 可以在处理一个词时，同时关注句子中其他相关位置，从而直接分析不同词之间的关系。

这种架构带来了几个关键优势：它更适合并行计算，更容易充分利用 GPU、TPU 等硬件，也更容易扩展到大规模数据和大规模模型，同时能够更有效地处理长距离的信息关联。

此后，BERT、GPT、GPT-2 等模型不断验证 Transformer 的扩展潜力。一个越来越清晰的方向开始出现：**当模型、数据和算力持续扩大时，模型能够学习到越来越丰富的语言规律和知识。**

## 1.6 大语言模型：从专用模型到通用能力

传统 AI 往往针对不同任务分别训练模型，例如分类、翻译、摘要各自使用不同系统。大语言模型则逐渐形成了另一种思路：

**先在海量文本上进行预训练，再通过同一个模型完成多种语言任务。**

GPT-3 等模型进一步展示了这种路线的潜力。随着模型参数、训练数据和计算资源不断增加，模型表现出明显的 **Scaling** 现象：规模扩大之后，很多能力也会随之增强。

与此同时，人机交互方式也发生了变化。开发者不再一定需要重新训练模型，而可以直接通过 **Prompt** 描述任务；模型还可以根据少量示例完成 Few-shot Learning，甚至利用当前对话中的信息进行 In-context Learning。

2022 年 ChatGPT 的出现是一个重要应用节点。它的意义并不只是模型性能进一步提升，而是让普通用户第一次能够通过非常自然的对话方式使用通用 AI。大语言模型由此迅速从研究模型走向实际的软件产品和开发平台。

## 1.7 从大语言模型到 API / SDK

随着 OpenAI、Claude、Gemini、DeepSeek、Qwen、Llama 等模型生态不断发展，一个新的问题逐渐从“如何训练模型”转变成了“**应用程序如何使用模型**”。

大语言模型通常需要大量计算资源，绝大多数普通软件并不会自己训练甚至部署模型，而是通过网络调用已经运行在服务器或云端的模型服务。因此，现代 AI 应用逐渐形成了一条典型调用链：

**Application → SDK / API → Large Language Model**

最基础的方式是直接发送 HTTP 请求，但真正进入工程实践后，很快会遇到新的复杂度。不同模型服务可能采用不同的 Authentication 方式，请求和响应的数据结构不同，Streaming 流式输出协议不同，Error Handling、Model Configuration 以及 Tool Calling 等能力也存在差异。

如果应用程序直接面向每一家模型服务编写调用代码，就会产生大量重复的网络通信、JSON 序列化、异常处理和协议适配逻辑。一旦需要更换模型或同时支持多个厂商，维护成本还会进一步上升。

因此，**LLM SDK** 开始成为应用程序与模型服务之间的一层工程抽象。它可以负责封装网络通信、管理认证信息、统一请求与响应结构、处理流式输出、统一错误处理，并尽可能降低不同模型厂商之间的接入差异。

这也正是本项目的出发点：**从零设计并实现一个 C++ 大语言模型接入 SDK，通过这个过程理解一个现代 LLM SDK 从网络通信、数据序列化、API 抽象到多模型接入的完整工程实现。**

回顾整个过程，人工智能的发展并不是某一种算法突然取代另一种算法，而是在不断解决上一阶段暴露出来的问题：从人工编写知识规则，到让机器从数据中学习；从依赖人工特征，到深度网络自动学习表示；再到 Transformer 支撑大规模预训练，最终形成具备通用能力的大语言模型。当这些模型开始作为一种远程计算能力进入软件系统后，问题自然从“如何构建智能”进一步延伸到了“如何可靠、统一、低成本地接入智能”。

# 2. 名词解释

## 2.1 【模型 - Model】

此处模型专指AI领域的模型。可以简单理解成**一个从大量数据中学习规律、用于进行预测的数学函数**。

可以把它类比成一个“看了大量猫狗图片后学会区分猫和狗的人”。

一开始，他并不知道猫和狗有什么区别。随着看到越来越多已经标注好的图片，他会慢慢总结出一些规律，比如耳朵、脸型、毛发等特征。

之后再给他一张从未见过的图片，他就可以根据之前学到的规律判断：
```
输入：一张新的动物图片
        ↓
      模型
        ↓
输出：这更可能是一只猫
```

## 2.2 【大模型 - Large Model】

大模型就是**参数规模大、训练数据多、计算量高，并具备较强通用能力的 AI 模型**。

“大模型”是一个比较宽泛的概念，它可以处理不同类型的信息，例如文本、图片、音频等。

根据主要处理的信息类型不同，大模型还可以进一步分为大语言模型、视觉模型、多模态模型等。

## 2.3 【大语言模型 - Large Language Model - LLM】

大语言模型是**专门用来理解和生成自然语言的大模型**。

它通过学习海量文本数据，掌握语言中的词语关系、表达方式和上下文规律，因此可以完成很多和语言相关的任务，比如：对话、写作、翻译、总结、代码生成、问答等。

像 `GPT、Claude、Gemini、DeepSeek、Qwen` 都属于大语言模型。

**大语言模型的局限性**：

- **幻觉（Hallucination）**：模型可能生成看起来合理、实际上错误或不存在的信息。
- **并不等于真正理解**：模型主要通过学习大量数据中的语言规律来生成结果，并不意味着它像人一样真正理解世界。
- **知识可能过时**：模型掌握的信息通常受训练数据和外部工具能力限制，不一定包含最新内容。
- **对输入比较敏感**：不同的提示词、上下文或表达方式，可能导致不同结果。

## 2.4 【提示词 - Prompt】

提示词就是**用户发送给大语言模型的输入内容或指令**，用于告诉模型“你想让它做什么”。

提示词三要素：
1、角色设定`Role`：
```
"你是⼀个具有⼗年以上C++后端开发的架构师，请帮我设计类似微信的聊天软件"
```
2、任务描述`Task`：
```
"⽤200字总结导致拖延症原因"
```
3、格式约束`Format`：
```
"请按要点分条列出，每条不超过15字"
```

通常来说，Prompt 描述得越清楚，模型就越容易理解你的需求并生成符合预期的结果。

## 2.5 【上下文 - Context】

上下文就是**模型在当前这次交互中能够看到并参考的信息**。

它不仅包括你刚刚发送的问题，还可能包括前面的聊天记录、系统提示词、文档内容等。

例如：
```
用户：我叫小明。
用户：我今年 20 岁。
用户：请问我叫什么名字？
```
模型之所以能回答“小明”，就是因为前面的内容还在它的上下文中。

但注意，模型不会记住所有上下文信息，超出部分会被丢弃。

## 2.6 【Token】

Token 是**大语言模型处理文本时使用的基本单位**。

我们日常使用的自然语言像汉语或英语，是按字或词作为基本单位的，但模型并不是直接按照“一个字”或“一个单词”来理解文本，而是会先把文本切分成一个个 Token 来处理。

## 2.7 【多模态 - Multimodal】

多模态指的是**AI 不仅能处理文本，还能同时理解和处理图片、音频、视频等多种类型的信息**。

例如一个多模态模型可以：

- 看图片并回答问题
- 听语音并转成文字
- 根据文字理解图片内容
- 同时结合文字和图片进行分析

这里的“模态”可以简单理解为**信息的不同形式**，比如文本是一种模态，图片也是一种模态。

## 2.8 【API - Application Programming Interface】

API 就是**一个程序提供给其他程序调用功能的接口**。

在大模型场景中，应用通常不会直接操作模型本身，而是通过 API 向模型服务发送请求，再获取返回结果。

例如：
```
C++ 程序
   ↓
  API
   ↓
大语言模型
   ↓
返回回答
```

## 2.9 【SDK - Software Development Kit】

SDK 就是**为了方便开发者使用某项服务或能力而提供的一套开发工具集合**。

它通常会把底层复杂的操作封装起来，让开发者通过更简单的代码完成调用。

例如调用大模型时，如果直接使用 API，可能需要自己处理：
```
HTTP 请求
JSON 数据
身份认证
错误处理
流式响应
```
而使用 SDK 后，通常只需要调用几个封装好的函数即可。
```
应用程序
   ↓
  SDK
   ↓
  API
   ↓
大语言模型
```
可理解为 SDK 就是对 API 和相关开发流程进行进一步封装，让开发者更方便地使用某项能力。


# 3. 项目架构

本项目整体采用分层架构设计。系统外部由浏览器客户端发起请求，项目内部主要划分为 **应用层、SDK 层和第三方服务层**。

![485](QQ_1787843160598.png)

1. 应用层：应用层主要由 `ChatServer` 组成，负责接收浏览器客户端发送的 HTTP 请求，并调用 `ChatSDK` 完成聊天功能。
2. SDK 层：SDK 层是项目的核心部分，对上层提供统一的大模型调用接口，并封装具体的模型管理、会话管理和数据存储逻辑。
	- `LLMManager`：负责管理不同的大模型 Provider
	- `SessionManager`：负责管理会话和多轮对话上下文
	- `SQLite`：负责持久化保存会话和聊天记录
3. 第三方服务层：由实际提供大模型能力的平台组成。SDK 中对应的 Provider 通过 HTTP 请求调用这些模型服务，并将不同平台的请求和响应格式进行统一封装。
4. 系统的一次完整聊天请求流程如下：
	```
	用户
	 ↓
	浏览器客户端
	 ↓ HTTP
	ChatServer
	 ↓
	ChatSDK
	 ↓
	SessionManager 获取会话上下文
	 ↓
	LLMManager 选择对应 Provider
	 ↓
	Provider 调用第三方大模型服务
	 ↓
	返回模型结果
	 ↓
	SessionManager 保存聊天记录
	 ↓
	ChatServer 返回结果给浏览器
	```
